## 4. Обновления: как вносятся все изменения

**4.1. Принцип.** Любое изменение на сервере вносится только файлом `obnovlenie_N.zip`. Руководитель ставит его в Экосистеме → Обновления, можно с телефона. Можно выбрать несколько файлов сразу, они встанут по порядку номеров. Перед заменой старые файлы сохраняются, кнопка «Вернуть как было» откатывает последнее обновление.

**4.2. Номер.** N = номер последнего установленного + 1, в описи `needs` = N − 1. С другим номером сервер файл не примет. На 13.11.2026 последний установленный — №530. Номер общий для Claude и для помощника DeepSeek.

**4.3. Что внутри архива**
- `manifest.json`: `{"n", "needs", "title", "what": [пункты по-русски для руководителя], "cats": [], "files": [{"p": путь, "h": sha256 файла}]}`.
- `sig.txt`: HMAC-SHA256 от точных байтов manifest.json, ключ — строка UPD_KEY (64 hex-символа как текст). Подпись записывается в hex.
- Пути файлов:
  - `site/…` → папка сайта itcpartner.ru;
  - `store/…` → магазин itcpartner.store (api/, apps/<имя>/, eco/, index.html…);
  - `metro/…` → «Мой Гуанчжоу»;
  - `seed/…` → новые фабрики (в базу их переносит страница обновлений);
  - `hk/…` → «почта» для Гонконга (4.5).
- Эти файлы сервер не заменяет никогда: config.php, upd_key.php, suppliers.php, .htaccess, state.json, ya.json, ds_key.json.
- Если правите приложение (`store/index.html` или `store/apps/<имя>/index.html`), поднимите номер кэша в соседнем `sw.js` (например `itc-fil-v24` → `itc-fil-v25`). Иначе у людей останется старая версия.

**4.4. Сборка (Python)**
```python
import json, hashlib, hmac, zipfile
def build(n, title, what, files, upd_key, out):   # files: {"store/apps/fil/index.html": bytes, ...}
    sha = lambda b: hashlib.sha256(b).hexdigest()
    man = json.dumps({"n": n, "needs": n - 1, "title": title, "what": what, "cats": [],
                      "files": [{"p": p, "h": sha(b)} for p, b in files.items()]},
                     ensure_ascii=False, indent=1).encode()
    sig = hmac.new(upd_key.encode(), man, hashlib.sha256).hexdigest()
    with zipfile.ZipFile(out, "w", zipfile.ZIP_DEFLATED) as z:
        z.writestr("manifest.json", man); z.writestr("sig.txt", sig)
        for p, b in files.items(): z.writestr(p, b)
```
Перед отправкой проверить: `node --check` для .js, `php -l` для .php, подпись и хэши готового архива.

**4.5. Обновления для Гонконга**
- Внутри обычного обновления лежит папка `hk/`:
  - `hk/_manifest.json`: `{"n", "title", "post": "команды bash после установки (можно не указывать)", "files": [{"p": путь внутри hk/files/, "h": sha256}]}`;
  - `hk/_sig.txt`: base64 подписи Ed25519 точных байтов hk/_manifest.json ключом HK_SIGN_KEY;
  - `hk/files/<p>`: файлы. На сервере они встают в `/opt/itc/<p>` (например `www/api/trade.php` → `/opt/itc/www/api/trade.php`).
- Все hk-файлы перечисляются и в основном manifest.json.
- Робот на сервере забирает «почту» раз в минуту и отчитывается. В Экосистеме → Обновления появляется строка «Гонконг: на связи · установлено №…».
- Открытая часть ключа лежит на сервере в `/etc/itc-hk/sign.pub`. Её заменили 13.11.2026, новый ключ проверен обновлением №530.

Задания серверу в Гуанчжоу.** В обычное обновление кладётся файл `store/uploads/srv_jobs/<id>.json`: `{"id", "title", "script": "команды bash", "sig": base64 подписи Ed25519 строки id + "\n" + script ключом SERVER_AGENT_SIGNING_KEY}`. Помощник на сервере опрашивает Экосистему раз в 2 минуты и выполняет только подписанные задания. Результат виден в Экосистеме. **4.8. Версии «Космоса»**
- Пакет сервера кладётся в магазин обычным обновлением:
  - `store/uploads/kosmos/pkg/kosmos-<версия>-<метка>.tar.gz` — сам пакет;
  - `store/uploads/kosmos/pkg/<версия>.json` — версия, sha256, подпись и открытый ключ.
- Подпись — Ed25519 над строкой `kosmos\n<версия>\n<sha256>`, ключом KOSMOS_SIGN_KEY. Сервер «Космоса» проверяет её открытым ключом /etc/kosmos/sign.pub, записанным при установке. Пакет с чужой подписью не ставится.
- Сервер раз в 10 минут проверяет, нет ли новой версии, и ставит её сам. База, ключи и настройки при этом не трогаются.
- Сборка: исходники «Космоса», папка `tools`.
  - `build_pkg.py` — только пакет;
  - `build_store_update.py --n <номер> --upd-key upd_key.php --sign-key kosmos_sign.pem --out obnovlenie_<номер>.zip` — готовое обновление магазина с пакетом, страницей и api/kosmos.php.
- Версия записана в `lib/boot.php` (KOSMOS_VERSION). Перед новой сборкой её поднять.

## 13. Как обновлять этот документ

Правило для любого помощника: изменение не считается сделанным, пока сейф и паспорт не обновлены.

После каждого изменения (новый ключ или пароль, новое приложение, сервер, сервис, срок оплаты):
1. Занести или исправить секрет в Bitwarden: нужный проект, понятное имя, заметка «что это, откуда, где лежит на сервере».
2. Обновить этот паспорт: нужный раздел, дату вверху и строку в журнале (раздел 14).
3. Пересохранить паспорт в Bitwarden: проект `dev` → `SYSTEM_HANDOVER` (разделы 0–4), `SYSTEM_HANDOVER_2` (5–10а), `SYSTEM_HANDOVER_3` (11–12), `SYSTEM_HANDOVER_4` (13–14). Сейф принимает в одну запись не больше 35 000 знаков в зашифрованном виде (около 26 000 байт текста, русского — примерно 14 000 знаков); если часть вырастет, делить дальше по разделам (`SYSTEM_HANDOVER_5`). Главная копия — в GitHub, `docs/ITC_pasport_sistemy.md`.
4. Прислать файл руководителю в чат.

Как это делается технически: помощник работает с сейфом через встроенный браузер на ноутбуке руководителя, где руководитель вошёл в Bitwarden. Из облачной среды Claude сервер Bitwarden напрямую недоступен. Чтобы руководителю не входить каждый раз, при входе можно отметить «Не спрашивать на этом устройстве 30 дней», а в настройках сейфа увеличить время до блокировки.

Следующий этап, по желанию: отдельный пропуск (машинный аккаунт) для серверов, чтобы они сами брали ключи из сейфа.
